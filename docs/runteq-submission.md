## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

物流現場では、同じ「件数」であっても、実際の負担が大きく異なる場面を何度も見てきました。

例えば、

- 件数は少ないが荷物の個数が多いコース
- 配達先が広く散らばっていて移動距離が長いコース
- 配達先が密集していて短時間で多く回る必要があるコース

など、表面的な件数だけでは見えない負担差があります。

しかし実際の現場では、件数ベースで比較されることが多く、  
「今日はこのコースが重い」  
「この担当ばかり大変」  
といった感覚的な不満が生まれても、それを客観的に説明することが難しい状況がありました。

私はこの状況に対して、**負荷を感覚ではなく、データとして可視化できないか**という問題意識を持ったことが、このアイデアの出発点です。

### 2-2. なぜそれが「気になった」のか

私はこれまで、現場で起きている困りごとを整理し、構造化し、改善につなげることにやりがいを感じてきました。  
そのため、「なんとなく不公平」「でも説明できない」という状態を放置することに強い違和感がありました。

また、配送現場における負担の偏りは、単なるその日の不満ではなく、

- 現場の納得感の低下
- モチベーションの低下
- 配分判断への不信感
- 長期的には業務運用の不安定化

にもつながり得ると感じています。

そのため、自分にとってこの課題は単なる不便ではなく、  
**現場改善のために向き合うべき構造的な問題**として強く意識されました。

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

配送コースごとの業務量を比較するとき、件数ベースでしか見られないことが多く、実際の負担差が分かりにくいことです。

### 3-2. 本当に解決したい課題は何か

- なぜ困るのか？  
  → 件数だけでは実際の負荷差が見えず、不公平な配分が起きやすいから。

- なぜそれが問題なのか？  
  → 担当者が「自分ばかり大変」と感じやすく、現場で納得感を持てないから。

- なぜ納得感が重要なのか？  
  → 納得感のない状態は、不満の蓄積やモチベーション低下につながり、継続的な安定運用を難しくするから。

**→ 本当に解決したい課題：**  
配送現場において、業務負荷の偏りを客観的に把握できず、公平な判断や納得感ある運用が難しいこと。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

#### 年齢設定
- 年齢：30代〜50代
- 理由：配送業務の差配や日々の運用判断、業務改善の判断を担う立場にいることが多い年代であるためです。

#### 生活・状況設定
- 生活・状況：物流会社や配送拠点で、日々のコース配分、配達実績の確認、現場の進行管理を担当している
- 理由：どのコースが重いか、偏りが続いていないかを判断する必要があるためです。

#### 環境設定
- 環境：配送実績データは存在するが、判断は件数や経験則ベースになっている現場
- 理由：既存の運用では見えない負荷差を、スコア化と可視化によって補えるためです。

### 4-2. 自分とユーザーの距離

- 身近な誰か、かつ自分自身に近い存在

物流現場に近い立場で課題を見てきたため、机上の想像ではなく、実際の現場感覚や問題意識をもとに設計しています。  
そのため、想定ユーザーとの距離はかなり近いと考えています。

### 4-3. 実際に使われる可能性について（需要・存在確認）

- まず最初に使ってくれそうな人は誰か？  
  → 配送コースの配分や日々の実績確認を行う管理者・責任者

- その人は、どんな場面でこのアプリを思い出すか？  
  → 「今日はどのコースが重かったか」「負担が偏っていないか」を確認したい場面

- 今の生活の中で、代わりに使っているものは何か？  
  → Excel、紙資料、担当者の経験則、口頭共有

- それを置き換えてまで使う理由はあるか？  
  → 感覚ではなく数値で説明できるため、公平性や納得感のある判断につながるから

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ（導入・継続の流れ）

- どんな場面・困りごとがきっかけで、このサービスを知る・思い出すか  
  → コース間の負担差が問題になったとき、または現場内で不公平感が生まれているとき

- 最初の一歩（登録・導入）で、ユーザーは何をする必要があるか  
  → コース情報や配送実績CSVを登録し、日別の実績を確認する

- 利用を続ける理由は何か？  
  → 単日だけでなく、週次・月次での偏りの傾向を見ながら、改善結果を確認できるから

#### toB向けサービスとして意識している点

- 企業や組織が、このサービスを導入する判断をする理由は何か  
  → 負担の偏りを可視化し、説明可能な配分判断を支援できるため

- どうしたら機密情報や業務データを、個人開発のサービスに登録したいと思ってもらえるか  
  → まずは限定的な範囲・小規模な利用から始め、扱うデータの範囲や運用方法を明確にすることが必要と考えています

- 既存の運用やツールから、乗り換えるハードルはどこにあるか  
  → 新たな入力作業の負担や、今までの経験則中心の判断を変える心理的ハードルがあると考えています  
  → そのため、CSV取込によって既存データを活用しやすくする設計を意識しています

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

本アプリと完全に一致する目的のサービスは、現時点で自分が調査した範囲では確認できませんでした。  
ただし、現場では以下のような手段が、実質的な代替手段として使われていると考えています。

#### 代替手段①：Excel / Googleスプレッドシート
- どんなことができるか：
  - 配送実績の入力
  - 件数や個数の集計
  - 表形式での比較
- 足りない点・不便な点：
  - 件数・個数・距離・密度など複数要素を一貫した考え方で負荷として評価しにくい
  - 集計や比較のルールが属人化しやすく、判断根拠を共有しづらい

#### 代替手段②：紙資料・口頭共有・経験則
- どんなことができるか：
  - 当日の状況把握
  - 現場感覚をもとにした配分判断
- 足りない点・不便な点：
  - 履歴が残りにくく、後から振り返りや比較がしづらい
  - 「なぜその判断になったのか」を説明しづらく、納得感に差が出やすい

#### 代替手段③：既存の配送管理システム
- どんなことができるか：
  - 配送進捗管理
  - 配車管理
  - 実績管理
- 足りない点・不便な点：
  - 配送全体の管理には向いていても、
    **コースごとの負荷の偏りを比較し、公平な配分判断を支援すること**
    に特化していないことが多い

### 5-2. それでも自分が作りたい理由

現場では、ExcelやGoogleスプレッドシート、紙資料、口頭共有、既存の配送管理システムなど、近い役割を果たす手段はすでに存在しています。  
しかし、それらは主に「実績を記録する」「進捗を管理する」「その場で判断する」ためのものであり、  
**配送コースごとの負荷の偏りを、複数要素をもとに比較し、納得感ある配分判断につなげること**
を主目的としたものではないと感じています。

自分が解決したいのは、単にデータを一覧で見られるようにすることではなく、  
**件数だけでは見えない負荷差を、現場で説明可能な形にすること**です。

そのため、既存の代替手段では埋めきれない部分に対して、  
現場課題から発想した形で価値を出せるサービスを作りたいと考えました。

### 5-3. 差別化を一文で決める

- 私のアプリの差別化ポイント：  
  **配送現場の管理者が、件数だけでは見えない負荷の偏りを客観的に把握し、感覚だけに頼らず根拠を持って配分判断できるようになる点**

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- 行動の変化：  
  感覚ではなく、データをもとにコース配分や振り返りができるようになる

- 気持ちの変化：  
  「なぜこの判断なのか」が見えることで、納得感を持ちやすくなる

- 考え方の変化：  
  件数中心の見方から、複数要素を踏まえた業務負荷の見方へ変わる

### 6-2. 価値を一文で表す

**このサービスは、配送現場の管理者が、コースごとの負担差を客観的に把握し、公平で納得感のある判断ができるようになるサービスです。**

## 7. このアプリで実現すること

### MVPで作る機能

本アプリの核となる価値は、  
**「配送コースごとの負荷の偏りを、件数以外の複数要素も踏まえて可視化し、配分判断の納得感を高めること」**  
だと考えています。

その価値を最小限で検証するために、MVPでは以下の機能を対象とします。

- 配送コースの登録・管理
- 配送実績CSVの取込
- 負荷スコアの算出
- Dashboard（日別のコース別負荷一覧表示）

これにより、まずは
**「件数だけでは見えない負荷差を、日々の実績ベースで比較できるか」**
を検証します。

### 本リリースで作る機能

MVPで価値検証を行ったうえで、本リリースでは以下のように拡張していきます。

- 単日・週次・月次での比較分析
- ダッシュボードでの可視化強化
- 従業員アカウント・設定管理
- より継続的な振り返りを可能にする分析機能の拡充

本リリースでは、単日の確認だけでなく、
**継続的に負荷の偏りを把握し、業務改善につなげられる状態**
を目指します。

## 8. このアプリの懸念点とその対策

### 懸念点①

- 何が問題になりそうか：  
  スコアの算出方法に対して、現場で「本当に実態を表しているのか」と感じられる可能性がある

- なぜそう思うか：  
  現場の負荷は複雑であり、単純な数式だけで完全に表現することは難しいため

- そのために考えている対策：  
  算出根拠を説明できる形にし、今後は係数や算出条件を調整しやすい設計を検討する

### 懸念点②

- 何が問題になりそうか：  
  toBサービスとしては、導入ハードルが高い可能性がある

- なぜそう思うか：  
  業務データを扱うため、信頼性・運用負荷・既存業務との整合が重要になるため

- そのために考えている対策：  
  まずは限定的な範囲・小規模な利用から始められる設計とし、CSV取込など既存運用を活かせる形を意識する

## 9. 今後の展開・発展の方向性

### 今考えている発展案

- 機能追加の方向性：  
  コース別の傾向分析、改善提案、比較指標の拡充

- UI・体験の改善：  
  より直感的に「どこが重いか」が伝わるダッシュボードやグラフ表現の改善

- 機能以外の工夫：  
  定期的な振り返り資料として活用しやすい出力や共有方法の検討

### 継続利用によって生まれる価値

日々の配送実績を蓄積することで、単日の振り返りだけでなく、  
週次・月次単位で偏りの傾向を把握できるようになります。

その結果、場当たり的な対応ではなく、  
継続的な業務改善につなげられるサービスにしたいと考えています。

### 10-2. 技術選定の理由

- なぜこの技術を使うのか  
  → RailsはWebアプリケーションを迅速に構築しやすく、CRUD、認証、管理画面など業務系アプリとの相性が良いと考えたためです。

- 今回チャレンジしたい点  
  → CSVを用いた業務データ取り込み、スコア計算ロジックの実装、分析画面の可視化、AWS環境での本番運用

- 不安な点  
  → 実際の業務現場に耐えうる設計や、toB向けサービスとしてのセキュリティ・運用面については、今後さらに深めていく必要がある点
